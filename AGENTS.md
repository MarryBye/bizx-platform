# AGENTS.md — Правила и протоколы работы AI-ассистента в BizX Platform

Данный документ является главным регламентом поведения AI-ассистента (агента) в проекте `bizx-platform`. Все правила обязательны к строгому исполнению во всех сессиях разработки.

---

## 1. Запрет на несанкционированную установку зависимостей

1. **Строгий запрет:** Агенту **категорически запрещено** самостоятельно запускать `pnpm add`, `npm i`, `yarn add` или редактировать секции `dependencies`/`devDependencies` в `package.json` без предварительного явного одобрения пользователя.
2. **Процедура запроса разрешения:**
   - Если для реализации фичи или решения задачи требуется новая библиотека, агент обязан **приостановить действие** и обратиться к пользователю.
   - Запрос должен содержать:
     - Название пакета и целевой модуль (`apps/...` или `packages/...`).
     - Зачем он нужен и какую задачу решает.
     - Плюсы (удобство, производительность, надежность) и минусы (размер бандла, количество транзитивных зависимостей).
   - **Действия при отказе:** Если пользователь не согласовал установку (или отклонил запрос), агент **обязан** найти решение задачи исключительно стандартными средствами языка и уже установленными в монорепозиторий библиотеками.

---

## 2. Согласование глубокого рефакторинга и ломающих изменений

1. В любых ситуациях, связанных с:
   - Глубоким рефакторингом архитектуры или существующих модулей;
   - Изменениями, ломающими обратную совместимость (breaking changes);
   - Спорными техническими решениями, где есть несколько альтернатив,
2. **Обязательный порядок действий:**
   - Агент **не применяет** изменения автоматически.
   - Агент подробно описывает текущую проблему/ситуацию.
   - Агент предлагает пользователю на выбор варианты решения (Вариант 1, Вариант 2 и т.д.) с описанием плюсов и минусов каждого пути.
   - Агент **обязательно** оставляет возможность выбора: _"Свой вариант пользователя"_ или _"Не делать эти изменения вовсе"_.
   - Работа продолжается только после того, как пользователь подтвердил выбранный путь.

## 3. Формат оформления коммитов (Conventional Commits)

Все коммиты должны строго следовать формату:

```text
type(module): action
```

### Допустимые типы (`type`):

- `feat`: новая функциональность
- `fix`: исправление ошибки или бага
- `refactor`: рефакторинг кода без изменения внешней логики
- `chore`: инфраструктурные задачи, конфиги, обновление скриптов
- `docs`: изменение документации
- `style`: форматирование кода, отступы, стили
- `test`: тесты

### Модули (`module`):

- `api` — NestJS бэкенд (`apps/api`)
- `landing` — Next.js сайт (`apps/bizx-landing`)
- `admin` — Vite React админка (`apps/bizx-admin`)
- `mobile` — React Native / Expo (`apps/bizx-mobile`)
- `ui` — библиотека компонентов (`packages/ui`)
- `database` — Drizzle ORM (`packages/database`)
- `common-types` — общие типы и Zod-схемы (`packages/common-types`)
- `infra` — Docker, compose, CI/CD
- `repo` / `root` — корень монорепозитория, конфиги Turborepo, pnpm

### Примеры коммитов:

- `fix(mobile): fixed incorrect button position`
- `chore(backend): better json response formatting`
- `docs(readme): updated readme`
- `feat(admin): added business profile page`
- `fix(api): handle invalid uuid in query param`

## 4. Регламент работы с Git и ветками

1. **Защищенная основная ветка (`main` / `master`):**
   - Прямой коммит и прямой пуш в основную ветку **полностью запрещены**.
   - Только пользователь лично решает, когда и какие Pull Request мерджить в основную ветку.

2. **Ветка `dev`:**
   - Ветка `dev` является базовой веткой разработки. Прямые коммиты в неё агенту также запрещены.
   - С ветки `dev` берутся актуальные обновления: перед началом задачи агент выполняет `git fetch` и `git pull` для ветки `dev`.

3. **Создание фиче-веток для задач (Feature / Fix branches):**
   - Каждая задача выполняется в отдельной ветке, созданной на базе свежей `dev`:
     ```text
     git checkout dev
     git pull origin dev
     git checkout -b <branch-name>
     ```
   - **Формат названия ветки:**
     `fix-<module>-<action-short>` или `feat-<module>-<action-short>`
     - _Примеры:_ `fix-mobile-button-layout`, `feat-api-health-check`, `chore-infra-docker-redis`.
   - Вся локальная работа, тесты и коммиты производятся **только** внутри этой ветки.

4. **Пуш и слияние:**
   - По завершении работы агент пушит созданную ветку на GitHub:
     ```text
     git push -u origin <branch-name>
     ```
   - Слияние (merge) ветки в `dev` выполняется пользователем через Pull Request в удобное для него время.
